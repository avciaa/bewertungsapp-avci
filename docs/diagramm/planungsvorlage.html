2. Zentrale Datenstruktur

Die Benutzerentscheidung bleibt die zentrale Datenquelle.

Die AI analysiert die vorhandenen Daten und erzeugt getrennte Vorschläge. Sie verändert nicht automatisch die Benutzerdaten.

USER → DECISION → DECISION_OPTION → PRO_CONTRA, ASSUMPTION, BENEFIT

Parallel dazu:

DECISION → AI_ANALYSIS → AI_SUGGESTION

und:

AI_ANALYSIS → DECISION_EMOTION → EMOTION

AI-Prinzip:

Die AI ist ein Analysewerkzeug und nicht die Quelle der eigentlichen Entscheidungsdaten.

Wenn ein Benutzer einen AI-Vorschlag akzeptiert, wird dieser explizit als Benutzerdaten übernommen bzw. neu erstellt.

4. Entitäten und Aufgaben

Entität Aufgabe
USER Benutzerkonto. Entscheidungen und Reflexionen werden einem Benutzer zugeordnet.
USER_PROFILE Persönliche Präferenzen und Entscheidungsfaktoren. Diese Daten können der AI als Kontext dienen.
DECISION Zentrale Entität einer Entscheidung. Enthält Frage, Kontext, Deadline und die optionale Referenz auf die tatsächlich gewählte Option.
DECISION_OPTION Vom Benutzer definierte Möglichkeit innerhalb einer Entscheidung.
PRO_CONTRA Pro- oder Contra-Argument für eine konkrete Option.
ASSUMPTION Unsichere Annahmen und mögliche unmittelbare, kurzfristige oder langfristige Konsequenzen einer Option.
BENEFIT Möglicher Vorteil einer Option.
PERSONAL_QUESTION Reflexionsfrage für den Benutzer. Kann entweder die gesamte Entscheidung oder eine konkrete Option betreffen.
MISSING_INFORMATION Informationen, die für die Entscheidung relevant sein könnten, aber noch fehlen.
AI_ANALYSIS Eine konkrete Ausführung der AI-Analyse. Dadurch können mehrere Analysen derselben Entscheidung unterschieden werden.
AI_SUGGESTION Einzelner Vorschlag der AI. Bleibt getrennt von den tatsächlichen Benutzerdaten.
EMOTION Katalog möglicher Emotionen für die spätere Reflexionswelt.
DECISION_EMOTION Verbindet eine AI-Analyse mit einer erkannten Emotion.
REFLECTION Spätere Selbstreflexion über eine Entscheidung. Mehrere Reflexionen pro Entscheidung sind möglich.

5. DECISION

Feld Typ Bedeutung
id PK Eindeutige ID der Entscheidung.
user_id FK Benutzer, dem die Entscheidung gehört.
question string Die eigentliche Entscheidungsfrage.
context text Zusätzlicher Kontext zur Entscheidung.
deadline datetime, nullable Optionale Frist.
final_option_id FK, nullable Verweist auf die tatsächlich gewählte DECISION_OPTION.
confidence integer, nullable Vertrauen des Benutzers in die eigene Entscheidung.
decided_at datetime, nullable Zeitpunkt der Entscheidung.
created_at datetime Erstellungszeitpunkt.
updated_at datetime Letzte Änderung.
Warum final_option_id?

Statt beispielsweise "Studium" als freien Text zu speichern, verweist die Datenbank direkt auf die Option.

Dadurch kann keine inkonsistente Kombination entstehen, bei der die gespeicherte finale Auswahl nicht zu den vorhandenen Optionen gehört.

6. DECISION_OPTION

Die Optionen werden vom Benutzer definiert. Die AI darf sie analysieren, aber nicht eigenständig umbenennen, löschen oder neue Optionen erzeugen.

Feld Typ Bedeutung
id PK Eindeutige Option-ID.
decision_id FK Entscheidung, zu der die Option gehört.
title string Name/Titel der Option.
description text, nullable Optionale Beschreibung.
created_at datetime Erstellungszeitpunkt.

7. Option-abhängige Daten

Diese Tabellen enthalten bewusst keinen decision_id mehr.

Die Zugehörigkeit zur Entscheidung kann immer über option_id → DECISION_OPTION → DECISION bestimmt werden.

Beispiel: 
DECISION
   |
   +-- DECISION_OPTION #27
          |
          +-- PRO_CONTRA
          +-- ASSUMPTION
          +-- BENEFIT

Option #27 gehört eindeutig zu genau einer Decision.

Dadurch wird eine fehlerhafte Kombination wie decision_id = 5 und option_id = 27, obwohl Option 27 zu Decision 8 gehört, verhindert.

9. ASSUMPTION

Feld Typ Bedeutung
id PK Eindeutige ID.
option_id FK Zugehörige Option.
assumption text Unsichere Annahme.
immediate_consequence text Mögliche unmittelbare Konsequenz.

long_term_consequence text Mögliche langfristige Konsequenz.

Deine aktuelle AI soll keine echten Wahrscheinlichkeiten schätzen. Deshalb setzt dein Code aktuell likelihood: "unknown".

Das Datenbankfeld kann daher zunächst nullable sein.

10. PERSONAL_QUESTION

Eine persönliche Frage kann sich entweder auf die gesamte Entscheidung oder auf eine konkrete Option beziehen.

option_id Bedeutung
NULL Frage betrifft die gesamte Entscheidung. Beispiel: "Was ist dir bei dieser Entscheidung am wichtigsten?"
Option-ID Frage betrifft eine konkrete Option. Beispiel: "Würde Option A dir mehr Unabhängigkeit geben?"

Deshalb ist option_id hier bewusst nullable.

11. AI_ANALYSIS

AI_ANALYSIS repräsentiert eine einzelne vollständige Ausführung der AI-Analyse. 

DECISION #42
    |
    +-- AI_ANALYSIS #1
    |      |
    |      +-- AI_SUGGESTION
    |      +-- DECISION_EMOTION
    |
    +-- AI_ANALYSIS #2
           |
           +-- AI_SUGGESTION
           +-- DECISION_EMOTION
Feld Typ Bedeutung
id PK Eindeutige Analyse-ID.
decision_id FK Entscheidung, die analysiert wurde.
prompt_version string Version des verwendeten AI-Prompts.
model string Verwendetes AI-Modell, z. B. das in GEMINI_MODEL konfigurierte Modell.
decision_tree JSONB, nullable Optional gespeicherter Entscheidungsbaum.

12. AI_SUGGESTION

Die AI erzeugt keine endgültigen Benutzerdaten. Sie erzeugt Vorschläge, die der Benutzer anschließend akzeptieren, bearbeiten, löschen oder ignorieren kann.

Feld Typ Bedeutung
id PK Eindeutige ID.
analysis_id FK AI-Analyse, aus der der Vorschlag stammt.
option_id FK, nullable Option, auf die sich der Vorschlag bezieht. NULL bedeutet: gesamte Entscheidung.
type enum/string Beispielsweise pro, contra, assumption, benefit, question, consequence.
content text Inhalt des AI-Vorschlags.
status enum/string pending, accepted oder rejected.
created_at datetime Erstellungszeitpunkt.
Wichtig:

AI_SUGGESTION wird niemals direkt zu PRO_CONTRA, ASSUMPTION oder BENEFIT, ohne dass die Anwendung dies explizit durch eine Benutzeraktion übernimmt.

13. Abgleich mit dem aktuellen AI-Code

Die aktuelle AI liefert pro Option genau einen Analyseblock.

AI Output Datenmodell
optionId DECISION_OPTION.id
pros PRO_CONTRA mit type = pro
cons PRO_CONTRA mit type = contra
benefits BENEFIT
assumptions ASSUMPTION
questions PERSONAL_QUESTION
branches aktuell Bestandteil von AI_ANALYSIS.decision_tree
missingInformation MISSING_INFORMATION
Wichtiger Punkt:

Dein aktueller AI-Code erzeugt keine confidence- oder likelihood-Werte. Diese werden bewusst von der Anwendung bzw. später vom Benutzer gesetzt.

Das passt zum Prinzip, dass die AI keine erfundenen numerischen Wahrscheinlichkeiten oder Bewertungen erzeugen soll.

14. Herkunft von AI-Informationen

Deine aktuelle AI verwendet drei mögliche basis-Werte:

basis Bedeutung
stated Information wurde vom Benutzer direkt angegeben.
inferred Information folgt logisch aus den vorhandenen Benutzerdaten.
conditional Information hängt von einer unbekannten Bedingung ab.

Im aktuellen Code wird daraus unter anderem die interne provenance erzeugt: 

stated      -> confidence: high
inferred    -> confidence: medium
conditional -> confidence: low
Wichtig: Diese technische Confidence beschreibt die Herkunft bzw. Sicherheit der Aussage und ist nicht dasselbe wie die persönliche Entscheidungs-Confidence des Benutzers.

15. Verschiedene Arten von Confidence

Das Datenmodell unterscheidet bewusst verschiedene Bedeutungen von "confidence".

Feld Bedeutung Empfohlener Bereich
DECISION.confidence Wie sicher ist der Benutzer bei seiner eigenen Entscheidung? 1–10
REFLECTION.confidence Wie sicher fühlt sich der Benutzer zum Zeitpunkt der Reflexion? 1–10
DECISION_EMOTION.confidence Wie sicher ist die AI, dass eine Emotion relevant erkannt wurde? 0–100
PostgreSQL: 
CHECK (confidence BETWEEN 1 AND 10)
bzw. bei der AI-Emotionserkennung: 
CHECK (confidence BETWEEN 0 AND 100)

16. Numerische Werte und Wertebereiche

Feld Vorschlag
confidence 1–10 für Benutzer-Confidence
importance 1–10
likelihood Muss vor der Implementierung eindeutig definiert werden. Entweder 0–1 oder 0–100.
DECISION_EMOTION.confidence 0–100 empfohlen.
Wichtig:

Die aktuellen AI-Prompts erzeugen keine echte Wahrscheinlichkeit für zukünftige Ereignisse.

Das Feld likelihood sollte daher nicht so verwendet werden, als würde die AI die Zukunft vorhersagen.

17. Emotionen und Reflexionsraum

Emotionen werden über eine separate Katalogtabelle verwaltet. Die Zuordnung zu einer AI-Analyse erfolgt über DECISION_EMOTION.

Emotion Beispiel für visuelles Element
Fear Geschlossene Truhe oder Schublade
Hope Licht durch ein Fenster
Long-term assumption Entfernte Tür oder Eingang

DECISION_EMOTION

Feld Bedeutung
analysis_id AI-Analyse, durch die die Emotion erkannt wurde.
emotion_id Erkannte Emotion.
confidence Confidence der Emotionserkennung.
evidence Textliche Grundlage bzw. Begründung für die Zuordnung.
created_at Zeitpunkt der Erkennung.

18. Reflection und späterer Rückblick

Eine Entscheidung kann nach mehreren Monaten erneut reflektiert werden. Deshalb besteht eine 1:n-Beziehung zwischen DECISION und REFLECTION.

Feld Bedeutung
what_decided Was wurde entschieden?
why_decided Warum wurde diese Entscheidung getroffen?
expected_outcome Was wurde erwartet?
fear Wovor hatte der Benutzer Angst?
hope Was wurde erhofft?
actual_outcome Was ist tatsächlich passiert?
confidence Confidence des Benutzers zum Zeitpunkt dieser Reflexion.
reflection_date Zeitpunkt der Reflexion.
Mehrere Reflexionen sind möglich.

Dadurch kann beispielsweise eine Entscheidung direkt nach dem Treffen, nach sechs Monaten und später erneut betrachtet werden.

19. Entscheidungsbaum

Dein aktueller AI-Code erzeugt: 

branches
  |
  +-- condition
  |
  +-- outcomes
        |
        +-- text
        +-- timeframe

Deshalb ist eine normalisierte Struktur mit drei zusätzlichen Tabellen für die aktuelle Implementierung nicht zwingend notwendig.

Stattdessen kann der komplette Baum als JSONB in AI_ANALYSIS.decision_tree gespeichert werden.

Beispiel: 
{
  "startingPoint": "Option A",
  "branches": [
    {
      "condition": "Wenn zusätzliche Kosten entstehen",
      "outcomes": [
        {
          "text": "Die Entscheidung wird erneut betrachtet.",
          "timeframe": "short_term"
        },
        {
          "text": "Weitere Informationen werden eingeholt.",
          "timeframe": "immediate"
        }
      ]
    }
  ]
}

Separate Tabellen für Branches und Outcomes können später ergänzt werden, falls Benutzer diese Elemente einzeln bearbeiten, durchsuchen oder versionieren sollen.

20. MISSING_INFORMATION

Die AI liefert auf Entscheidungsebene eine Liste missingInformation.

Diese Informationen können optional persistent gespeichert werden, wenn sie im Frontend vom Benutzer verwaltet werden sollen.

Feld Bedeutung
id PK
decision_id FK zur Entscheidung
content Fehlende Information
resolved Gibt an, ob die Information inzwischen geklärt wurde.
created_at Erstellungszeitpunkt
Falls missingInformation nur temporär im AI-Response angezeigt wird, könnte diese Tabelle auch weggelassen werden.

21. Randomizer / "Leave it to fate"

Der Randomizer benötigt in der aktuellen Version keine eigene Datenbanktabelle.

  • Choose A
  • Choose B
  • Think about it for another day
  • Ask someone you trust
  • Sleep on it
  • Flip a coin

Diese Funktion kann als Frontend-/Backend-Logik implementiert werden.

Eine eigene Tabelle wird erst notwendig, wenn die Anwendung historische Randomizer-Ergebnisse dauerhaft speichern soll.

23. Ablauf der AI-Analyse

  1. Benutzer erstellt eine DECISION.
  2. Benutzer erstellt die gewünschten DECISION_OPTION-Einträge.
  3. Das Backend sendet Decision + Profile an die AI.
  4. Die AI analysiert jede Option.
  5. Eine neue AI_ANALYSIS wird gespeichert.
  6. AI-Vorschläge werden als AI_SUGGESTION gespeichert.
  7. Emotionen können als DECISION_EMOTION gespeichert werden.
  8. Der Benutzer entscheidet selbst, welche Vorschläge übernommen werden.
Wichtig:

Die AI darf nicht automatisch die vom Benutzer erstellten Optionen verändern oder löschen.

24. Technische und sicherheitsrelevante Abgrenzung

Der API-Key gehört nicht in die Datenbank.

Er sollte im Backend als Secret bzw. Environment-Variable gespeichert werden, beispielsweise: 

GEMINI_API_KEY=...
GEMINI_MODEL=...
GEMINI_FALLBACK_MODELS=...
Illegale und gefährliche Inhalte:

Die Filterung solcher Inhalte gehört zur Backend-/AI-Logik und ist keine eigene Kernentität des ER-Modells.

26. Mögliche spätere Erweiterungen

Diese Tabellen sind für die aktuelle Architektur nicht zwingend erforderlich, könnten aber später sinnvoll werden:

  • Separate Tabelle für detaillierte AI-Provenance, falls sourceQuote dauerhaft gespeichert werden soll.
  • Separate Decision-Tree-Tabellen, falls Benutzer einzelne Branches bearbeiten können.
  • Randomizer-History, falls Zufallsergebnisse gespeichert werden sollen.
  • Versionierung von AI-Analysen und Prompts.
  • Speicherung der tatsächlich akzeptierten AI-Suggestion, falls eine detaillierte Audit-Historie benötigt wird.
Diese Erweiterungen sollten erst hinzugefügt werden, wenn die entsprechende Funktionalität tatsächlich benötigt wird.
